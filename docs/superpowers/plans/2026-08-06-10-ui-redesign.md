## Global constraints

All of CLAUDE.md applies. Binding highlights:

- **`data-astro-reload` on every `<form method="post">`.** Enforced repo-wide by
  `src/lib/astro-forms.test.ts`. This plan moves forms into sheets; a form in a
  portal is still a form.
- **No inline `onclick` anywhere in the client bundle.** An inline handler trips
  Cloudflare's API WAF and **403s the deploy** (survive-list #6). Every new
  control is a `data-*` hook read by an existing document-level delegated
  listener, capture phase where `preventDefault` is involved.
- **No new island.** The sheet, the menus and the now-playing surface are
  vanilla DOM built by `site.ts`, for the reason `shell-bundle.test.ts` already
  enforces: `Shell.astro` mounts on every page, so an island there ships to
  `/login`.
- **No new migration is expected.** If a task discovers it needs one: claim the

  back-date.
- **MIT header + the AGPL-combination note on every new file.**
- **Class renames are forbidden in the same commit as a visual change.** A
  selector in survive-list #7 that disappears produces **no build error** and no
  test failure until someone taps the control. If a rename is genuinely wanted,

### Task 0.1: the missing skip button

**Files:**
- Modify: `src/layouts/Shell.astro`, `src/scripts/site.ts`,
  `src/styles/global.css`
- Modify: `src/scripts/queue-wiring.test.ts`

**Rationale.** M6b shipped a queue, a drawer, autoplay advance and a
media-session `nexttrack` handler — and **no skip button in the UI**. A member
on a phone can skip from the lock screen but not from the app. This was designed
once already and reverted under the hold; the design is carried here verbatim
rather than re-derived.

The mechanism already exists at `site.ts:497`:

```ts
set('nexttrack', () => {
  if (getState().current === null) return
  handleAdvance({ type: 'SKIP', queue: renderedQueue })
})
```

That body becomes a named `skipToNext()` and gains a second caller. It is not a
second code path — it is a second trigger on one path, which is exactly what the
media-session handler already is.

**Design:**
- `#player-next`, a sibling of `#player-toggle` inside the persisted
  `.playerbar` div, immediately after it in DOM order.
- `type="button"`, `class="playertoggle"` (the transport class — **no `.btn`
  tier**, per the three-tier doctrine's transport exemption), `aria-label="Next
  track"`, glyph `⏭` for now (it becomes `Icon name="next"` in Task 1.2).
- **`hidden` in the markup, unhidden by `site.ts` at init and re-unhidden on
  `astro:after-swap`** — survive-list #10. Without JS there is no queue and no
  transport, so a visible skip button would be a control that does nothing.
- **Disabled when there is nothing to skip to.** `renderedQueue.length < 2` →
  `disabled`. Updated from `setRenderedQueue`, which is already the one writer.
- Dispatch is `handleAdvance({ type: 'SKIP', queue: renderedQueue })` — the
  literal `queue: renderedQueue` is **required**, not stylistic:
  `queue-wiring.test.ts` asserts by regex that every `SKIP` dispatch carries it,
  because a `.slice()` or a freshly assembled array reintroduces the stale-index
  bug.

**Survive-list touched:** #2 (persisted player node — a new id inside it), #6
(delegated events), #8 (button doctrine — the transport exemption), #10
(hidden-until-JS).

**Guard tests:** `src/scripts/queue-wiring.test.ts` (`dispatches SKIP with

### Task 0.2: safe areas and the viewport meta

**Files:** `src/layouts/Shell.astro`, `src/pages/login.astro`,
`src/styles/global.css`

screen, inside the iOS home-indicator gesture zone — a thumb drag on the

`calc(var(--bar-h) + env(safe-area-inset-bottom) + var(--pad-2))`, which
satisfies survive-list #17 by **deriving** the reservation instead of eyeballing
it. `--bar-h` lands here as a single declaration and Task 1.1 folds it into the
token block.

**Survive-list touched:** #5 (the chip's eyeballed offsets — this task does not
change them yet, but it introduces the token they will reference), #17 (the

### Task 1.1: tokens

**Files:** `src/styles/global.css`, new
`src/styles/global-tokens.test.ts`

**Rationale.** Spec §1. Today hierarchy has two rungs (`--line #000`,
`--faint #ddd`) and every component picks one by feel, which is why nothing has
a hover state worth the name — a border already at full black has nowhere to go.
The ladder gives border-opacity somewhere to travel, which is the single change
the owner asked for by name ("what changes are animations and borders").

**One relaxation, called out because it is a rule being removed.** The global
reset is:

```css
*, *::before, *::after { border-radius: 0; box-shadow: none; box-sizing: border-box; }
```

`border-radius: 0` stays — that is the 90° mandate and it stays enforced
globally. **`box-shadow: none` is deleted.** It is a blanket veto on the hard
offset shadow (the spec's signature device) *and* on the focus ring, which makes
it an accessibility bug wearing an aesthetic rule's clothes. It is replaced by
the rationing doctrine of spec §4.3, which is a stricter rule because a ration
needs judgement and "none" does not.

**Design:** the ink ladder, the border set, the surface ladder, `--pad-0/-4`,
`--tap`, `--bar-h`, the six motion values, the four easings, the global
`prefers-reduced-motion` block, the z-index ladder, the shadow scale.
`--faint` and `--mid` **stay as aliases** of `--ink-12` and `--ink-55` so this
lands in one reviewable commit and the ~40 call sites migrate per-surface in
Phase 3.

**Survive-list touched:** none directly. This is additive plus one deletion.

**Guard tests:** new `global-tokens.test.ts` reads `global.css` as text and
asserts:
- `border-radius: 0` survives in the global reset (the 90° mandate, asserted so
  a future contributor has to argue with a test);
- the six frozen greyscale tokens and the four `--btn-*` values are **unchanged
  byte-for-byte** — this is the "colour scheme stays same" mandate, made
  checkable;
- no `backdrop-filter` anywhere in the file (spec §1.5);
- exactly one `@media (prefers-reduced-motion` block (global, not per-component);
- no hex literal outside the `:root` block — tokens, not literals.

### Task 2.1: the sequential RPC chain — sin #1

**Files:** `src/pages/index.astro` (the M6c feed), `src/pages/pool.astro`,
`src/components/AppNav.astro`, `src/components/StorageChip.astro`,
`src/middleware.ts`; new `src/lib/page-data.test.ts`

**Baseline (audit §1.3):** every signed-in page render runs a **4–5-deep
sequential RPC chain** at 60–165 ms each = **~300–750 ms of server time per
view**, and because the UI is server-rendered with ClientRouter, *every* sort
click, filter change, search keystroke, pagination click and crate move runs the
whole chain again.

**Re-measured on the consolidated head (`1d1e1f8`), because M6c changed the
shape and the audit predates it:**

| Page | Stage 1 | Stage 2 | Stage 3 | Stage 4 | Sequential stages |
|---|---|---|---|---|---|
| `/` (feed) | `current_member()` | `Promise.all(feed×3 + crates)` | `review_pending_count()` | `my_storage()` | **4** |
| `/pool` | `current_member()` | `pool_list` | `pool_uploaders` | `review_pending_count()` → `my_storage()` | **5** |

M6c's feed **already parallelises its own four calls** (`index.astro:24`) —
credit where it is due, and it means the remaining cost on `/` is entirely the
two chrome calls. `/pool` still awaits `pool_list` and *then* `pool_uploaders`
(`pool.astro:27,35`) though they share no input.

**Acceptance criterion: at most 2 sequential awaits per page render, and page
server time ≤ 250 ms measured against the hosted project.**

**Design.** Three moves, in order of how much they buy:

1. **Parallelise `/pool`'s pair.** `pool_list` and `pool_uploaders` share no
   input and go into one settled batch.
2. **Stop blocking the frame on chrome data — the bigger win, and it applies to
   every page.** `my_storage()` renders a footer line; `review_pending_count()`
   renders a badge. Neither is above the fold, both are awaited *after* the
   page's own data because they live in components, and together they are two
   full round trips on the critical path of **every signed-in view**. Hoist both
   into the page's settled batch. The badge is additionally a candidate for a
   60 s `Astro.locals` cache, being owner-only and monotonic within a session.
3. **Composite RPC only if 1 and 2 miss the target.** A `page_pool(...)`
   returning rows + uploaders + counts in one round trip is one trip instead of
   two — but it is also a new definer function, a new grant, a new pgTAP file,
   and a new place for migration 20/28's column discipline to leak. Reach for it
   only with a measurement showing parallel calls were not enough.

**Survive-list touched:** #16 — the outage-vs-empty distinction, and it is the
one real hazard in this task. **Batching is safe with supabase-js specifically**
because `.rpc()` resolves to `{data, error}` rather than rejecting on a
PostgREST or HTTP failure — M6c's feed already depends on that and handles each
result's `error` individually (`index.astro:30-33`). That per-result branch is
the pattern to copy, and copying it is what preserves the distinction: a failed
`pool_uploaders` must render "the database is unreachable", never "you have
nothing". Use `Promise.allSettled` anyway for anything in the batch that is not
a supabase-js call, and **keep every existing `console.error` branch verbatim** —
they are the only signal an outage leaves.

**Guard tests:** new `page-data.test.ts` asserts by source read that no `.astro`
page has two `await …rpc(` calls outside one batch, and that every batched
result has its own `error` branch (the assertion that actually protects #16 —
the batching assertion alone would pass a page that silently swallowed a
failure); plus every existing page test stays green.

- [ ] **Step 1: measure.** `curl -w '%{time_starttransfer}'` against the hosted
      pool page, 10 samples, warm. **Record the number in the commit message** —
      an optimisation with no before-number is a guess.
- [ ] **Step 2: failing test** — `page-data.test.ts`.
- [ ] **Step 3: run, fail.**
- [ ] **Step 4: implement** moves 1 and 2 with `allSettled`, preserving every
      error branch and every EmptyState message path.
- [ ] **Step 5: green** + re-measure, same method. Target ≤250 ms.
- [ ] **Step 6:** if still over, implement move 3 with a migration, a pgTAP file
      and revoke-first grants.
- [ ] **Step 7: commit** — `perf(pages): parallelise the RPC chain (750ms → <N>ms)`

### Task 2.2: the pool page DOM — sin #2

**Files:** `src/components/TrackRow.astro`, `src/pages/pool.astro` (the
15-column table's home since M6c moved it off `/`), `src/styles/global.css`,
new `src/components/track-row.test.ts`

**Baseline (audit §1.4):** ~2.3 KB of HTML and **32 elements per row**;
`PAGE_SIZE = 100` → **~230 KB HTML (~30 KB gz) and 3,200+ elements** in one
tbody, rendered as a 15-column table with ~480 px of cell padding against a
375 px viewport and **no `overflow-x` container anywhere** — `.tracktable` has
no CSS rule at all.

Artist and title are each serialised **up to 8× per row**: `data-label`,
`data-artist`, `data-title` on the play link, the *same three again* on the
hidden `+Q` button, four `aria-label`s, and the two visible cells.

**Acceptance criterion: ≤10 elements and ≤700 B per row → a 100-row page under
~70 KB of HTML and under 1,000 elements. No horizontal page scroll at 375 px.**

**Design.** Two independent wins, both in this task because they touch the same
component:

1. **Kill the duplication.** `button.queueadd` drops
   `data-artist/-title/-duration/-bpm/-key` and keeps only `data-file-id`.
   site.ts already scrapes `a.play` inside `[data-queue-list]` to build the list
   a play means (survive-list #7) — the `+Q` handler reads the same link,

### Task 2.3: `/login` ships zero JavaScript — sin #3

**Files:** `src/pages/login.astro`, new `src/pages/auth/start.ts`, new
