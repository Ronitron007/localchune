# M6b — queue-centric playback (the queue engine)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One playback engine. A visible, capped queue that is *derived state* —
recomputed from scratch on every playback event, never mutated in place. Opt-in
autoplay, and a harmonic auto-queue that finally puts M3's key and BPM analysis on
the decks. Third and last of three M6 slices (spec:
[`2026-07-29-m6-org-layer-design.md`](../specs/2026-07-29-m6-org-layer-design.md) §8).

**Architecture:** Four pure TypeScript modules under `src/lib/` — model, strategies,
engine, store — plus one thin candidate-fetch route over the *existing* `pool_list`
RPC, plus DOM wiring in `src/scripts/site.ts` and one persisted drawer in
`Shell.astro`. **No migration. No new RPC. No new table.**

**Tech stack:** Astro SSR on Cloudflare, Supabase Postgres + pgTAP, vanilla
site-script JS (no island), vitest (node env).

**Branch:** `rohan/m6b-playback`.

---

## 0. The owner's directive, and what it means

Verbatim, across three messages:

> "we need to create a playback engine…where there are multiple ways to compute the
> array of the queued tracks. there is a hook that processes like playing a new
> track, skipping a track, adding a track in the queue, clicking a track in the
> queue etc call the engine to regenerate this queue…the queue is always 25 songs
> at max never more sometimes less…"

> "there is a queue that is generated based on user's choice..be it playing a crate,
> adding a song to the queue, and then there is auto-queue which can have different
> methods for the same…"

> "currently it will only be bpm and key based but in future we do genre based…
> artist based…create maps of artists and play tracks from similar artists and all
> that stuff…but at its core is one queue engine"

Four load-bearing consequences, each of which shapes a task below:

1. **ONE QUEUE ENGINE.** Named principle. There is exactly one module that decides
   what the queue array contains. Every surface — pool table, crate page, track
   page, the drawer, the lock screen — routes through it. No second code path
   builds a play order.
2. **The queue is derived, not mutated.** Every event produces a new state, and the
   engine recomputes the array from that state. There is no `queue.splice()`
   anywhere in this milestone.
3. **Two layers.** The user's explicit choices are one layer; the auto-queue is the
   other. Strategies regenerate only the second.
4. **The strategy interface is the durable contract.** BPM + key is all v1 computes.
   Genre (needs M8) and artist-similarity maps are future work, and they must land
   as *new files*, not as an engine rewrite. §3 states the boundary that makes that
   true.

## 1. The queue model

### 1.1 Three parts, not two

The state has three parts; the *layers* are two of them.

```
QueueState = {
  current: QueueEntry | null   // what is loaded in <audio> right now
  intent:  QueueEntry[]        // LAYER 1 — the user's explicit choices, in their order
  method:  AutoMethod          // which strategy fills LAYER 2. Default 'off'.
  history: string[]            // file_ids consumed this session, most-recent-first
  failed:  string[]            // file_ids whose source fetch or decode failed
  suppressed: string[]         // auto entries the user removed by hand this session
}
```

`current` is deliberately **not** a member of either layer. That one decision
dissolves the "does clicking an auto-queued track promote it to the user layer?"
question: a clicked entry leaves the layers and *becomes* `current`, so there is
nothing to promote and no special case to write. It also makes the seam the UI has
to draw honest — the drawer shows NOW PLAYING, then YOUR QUEUE, then UP NEXT · AUTO,
and those are three real fields, not three CSS classes over one array.

**Layer 1 — intent.** Every entry here is the deterministic consequence of an
explicit action, and the engine will never reorder, re-rank or drop one:

| Action | Effect on `intent` |
|---|---|
| Play a track from any row | **replaces** — the rest of that row's surrounding list, from the next row on |
| Play a crate (or a crate row) | **replaces** — the crate's remaining tracks in `position` order |
| `+ queue` on a track row | **appends** one entry (`origin: 'add'`) |
| `+ queue` on a crate card or crate page | **appends** the crate's tracks in `position` order (`origin: 'crate'`) |

Both replacing actions prompt first when the layer is non-empty — §1.5.

Every entry carries `origin: 'list' | 'crate' | 'add'` and `source_label` (the crate
name, or "pool", or the filter description) so the drawer can say *where these came
from* — which is the only way a user can tell layer 1 from layer 2 without reading
the code.

**Layer 2 — auto.** Computed fresh on every single regeneration, by the selected
`method`, and never persisted. It has no identity across regenerations: an entry
that survives two events survives because the strategy picked it twice, not because
anything held onto it.

### 1.2 The 25 cap, exactly — and it is the only cap

```
QUEUE_MAX = 25              // the owner's number. The whole array, current included.
```

```
slots  = QUEUE_MAX - (current === null ? 0 : 1)     // 24 while something plays
intent = intent.slice(0, slots)                      // ENFORCED ON WRITE, not on read
need   = slots - intent.length
auto   = need > 0 && method !== 'off' ? strategy.select({ ..., need }) : []
queue  = [current, ...intent, ...auto].filter(Boolean)   // length <= 25
```

**There is exactly one number, and nothing is stored beyond it.** An earlier draft of
this plan kept a 500-entry stored intent layer and showed only its first 24 — spec
§8's cap, carried forward. The owner's rule kills that: a hidden 476-entry backlog
*is* more than 25, whatever the drawer chooses to render. `INTENT_MAX` does not
exist. Truncation happens at the moment of the write, inside `reduce`, and it is
reported to the user.

Consequences, both stated here rather than discovered later:

- **Playing a 60-track crate plays its first 24.** The drawer's source line reads
  `warehouse · 24 of 60` and the status region says so once. The remaining 36 are not
  silently held anywhere; picking track 25 from the crate page is how you continue. A
  "continue this crate" affordance is a reasonable v2 ask and is deliberately not
  built here.
- **`+ queue` on a crate appends what fits.** With 20 entries already queued and a
  17-track crate added, four are appended and the status region says
  `added 4 of 17 from warehouse — queue is full (25)`. Silent partial success is the
  one outcome this must not have.
- **When `intent` alone fills the slots, the auto layer gets zero and no strategy
  runs** — and, importantly, **no network call is made**. The user's choices win the
  cap outright.

### 1.3 "Sometimes less" — the complete enumeration

The owner said "sometimes less". These are all the ways, and every one of them is a
test case in Task 1 or Task 2:

1. **`method: 'off'` — the default.** Layer 2 contributes exactly zero, by
   definition. A crate that drains to empty leaves a queue of length 1, then 0, and
   **playback stops**. This is now the ordinary case, not an edge: see §1.6.
2. **Small pool.** Fewer than 25 pool-visible tracks exist. The tail is what exists.
3. **Harmonic dead-end.** The seed's Camelot neighbourhood × its ±6 % BPM window
   returns fewer candidates than `need` after exclusions. The engine falls back to
   the `bpm` strategy *once* (BPM window only, key ignored); if that is still short,
   the queue is short. It does not widen the window and it does not retry — §3.4.
4. **Exclusions ate the candidates.** `current`, every `intent` entry, `history`,
   `failed` and `suppressed` are removed from the candidate set before any strategy
   sees it. A long session in a narrow BPM band shrinks its own tail; that is correct
   behaviour, not a defect.
5. **Unanalysed seed.** The current track has no `bpm`/`key_camelot` (analysis
   pending, or an M3 `failed` row its own uploader can still play — migration 16b).
   Harmonic cannot seed. Falls back to `bpm` if a BPM exists, else `shuffle`, else
   the tail is empty.
6. **Intent fills the slots.** §1.2. Layer 2 gets nothing.
7. **Nothing playing and nothing queued.** Length 0. The drawer renders `EmptyState`'s
   idiom, not an error.

### 1.4 The event hook

One reducer. Every listed event runs it; the engine then recomputes the array. There
is no other way to change the queue.

| Event | State transition |
|---|---|
| `PLAY_TRACK {file_id, list, index, source_label}` | **Confirm-gated (§1.5).** `history` ← push `current`; `current` ← the track; `intent` ← the rest of `list` after `index`, truncated to `slots` |
| `PLAY_CRATE {crate_id, items, start}` | **Confirm-gated (§1.5).** Same, with the crate's remaining items |
| `ADD_TO_QUEUE {entries}` | `intent` ← append, deduped against `intent` + `current`, truncated to `slots`; returns `{added, offered}` so the caller can report a partial append |
| `SELECT_QUEUE_ENTRY {index}` | entries before `index` are consumed into `history`; the entry at `index` becomes `current`; intent entries after it survive in order |
| `SKIP` | equivalent to `SELECT_QUEUE_ENTRY {index: 1}` |
| `TRACK_ENDED` | same as `SKIP`, and it is the *only* difference: `history` records it as played, not skipped |
| `REMOVE_QUEUE_ENTRY {index}` | intent entry → drop it from `intent`; auto entry → push to `suppressed` so the regeneration does not immediately put it back |
| `TRACK_FAILED {file_id}` | push to `failed`, then `SKIP` |
| `SET_METHOD {method}` | `method` ← new. **Nothing else changes.** |
| `CLEAR_QUEUE` | `intent` ← `[]`. `current` keeps playing. |

Four rules the table encodes, called out because they are the ones a reviewer will
want to argue with:

- **A strategy switch never touches layer 1.** `SET_METHOD` is one field. The pins
  survive, in place, in order. This is the direct answer to the "do pins survive a
  strategy switch?" tension: yes, structurally, because strategies cannot reach them.
- **Play replaces; `+ queue` appends** — for tracks and crates alike, one rule each,
  and they are companion affordances rendered next to each other everywhere.
- **Click-ahead drops what you jumped over.** `SELECT_QUEUE_ENTRY {3}` consumes
  entries 1–2 into history; they do not come back. This is what every player anyone
  has used does, and holding them would make "click the fourth track" mean "play the
  fourth track and then the two you just skipped". *(Owner-confirmed 2026-08-05.)*
- **`REMOVE_QUEUE_ENTRY` on an auto entry needs `suppressed`**, or the regeneration
  that immediately follows re-picks the track you just removed and the button looks
  broken. Session-scoped, never persisted.

### 1.5 Replacing a non-empty queue asks first

Owner, verbatim: *"User gets a modal…asking clear queue…and cancel."*

**The predicate is pure and lives in the engine.** `requiresClearConfirm(state,
event)` returns true for `PLAY_TRACK`/`PLAY_CRATE` when `state.intent.length > 0`,
and false for everything else — never for `SELECT_QUEUE_ENTRY` (clicking something
already queued is not a replace), never when the layer is empty. Putting it in the
engine rather than in `site.ts` is what keeps it testable and keeps the DOM half a
one-line call.

**The mechanism is `window.confirm()`, called from the existing delegated handler in
`site.ts`.** That is the house pattern: `site.ts` already runs a document-level
`submit` listener for `form[data-confirm]` that calls `window.confirm()`, and its
header comment records exactly why the call lives in the bundle and not in an inline
handler attribute — *Cloudflare's API WAF challenges a Worker upload whose bundle
contains inline handlers, and the deploy POST 403s with an HTML challenge page*.
Same primitive, same file, same reason.

The `data-confirm` **attribute** form is not reusable here, and the plan says why
rather than leaving the next reader wondering: it is unconditional and form-only.
This prompt fires only when the intent layer is non-empty — a static attribute cannot
know that — and the play control is an `<a class="play">`, not a form. So Task 6
calls `window.confirm()` directly from the play delegation, gated on the engine's
predicate. No new mechanism, no custom modal, no new markup.

Copy names what is lost, because "Are you sure?" is not a question anyone can answer:

```
Playing "warehouse" clears your queue of 7 tracks. Continue?
```

Two mechanics that matter:

- **Prompt before claiming the transport.** `site.ts` claims `currentFileId`
  *synchronously* on click — that is the documented guard that lets a click beat an
  in-flight restore. `confirm()` blocks, so it must be called **before** that claim
  and before any fetch. A cancel must leave the state byte-for-byte unchanged: no
  claim, no fetch, no history push, nothing.
- **A suppressed dialog reads as cancel.** Browsers offer "prevent this page from
  creating additional dialogs" after several rapid prompts, and a suppressed
  `confirm()` returns `false`. The play then does nothing, which is safe but could
  look broken — so the drawer's `CLEAR` button is the always-available manual path
  (clear, then play, no prompt). This is the one known weakness of `confirm()` here
  and it is judged acceptable: a custom modal would need focus trapping, an escape
  path, a backdrop and its own accessibility story, for a dialog this app shows at
  most a few times a session.

### 1.6 Autoplay is opt-in — default `off`

*(Owner-decided 2026-08-05.)* `method` starts at `'off'`. A queue that drains stops
playing; nothing is auto-appended until a member taps `MIX`, `TEMPO` or `SHUFFLE` in
the drawer. Three things follow, and all three are good:

- **Zero added network cost by default.** `method: 'off'` short-circuits before the
  candidate port is called, so a member who never opens the drawer never issues a
  single `pool_list` request for the queue. Task 3 asserts this with a spy.
- **The pool never plays something you did not ask for.** For a shared crate library
  that is the safer default.
- **The auto layer becomes a visible feature rather than ambient behaviour**, which
  is what the three-section drawer (§4) is for.

## 2. Data sources — and why nothing new is created

**`pool_list` already is the candidate query.** Migration 11 shipped
`camelot_neighbours()`, and `pool_list(p_key, p_harmonic, p_bpm_min, p_bpm_max,
p_half_double, p_tier_min, p_sort, p_limit)` already applies the exact narrowing the
harmonic strategy needs, already enforces pool visibility, already carries migration
28's provenance discipline, and is already `granted to authenticated` and to nobody
else. A `queue_candidates()` RPC would restate all of that, and would re-open the
column-grant question migrations 20 and 28 exist to have closed.

So: **no new RPC, no view change, no ACL surface.** Task 5 adds one thin Astro route:

```
GET /api/queue/candidates?key=8A&bpm=128&limit=200
  -> { candidates: TrackFeatures[] }
```

which calls `pool_list` server-side with

```
p_key: <seed camelot>, p_harmonic: true,
p_bpm_min: bpm * (1 - BPM_WINDOW), p_bpm_max: bpm * (1 + BPM_WINDOW),
p_half_double: false, p_sort: 'added_desc', p_limit: 200
```

and projects **only** the `TrackFeatures` subset onto the wire. That projection is
the point: `pool_list` returns forty-odd columns including `provenance`, and a queue
tail needs nine. Sending the rest to the browser on every regeneration would be both
wasteful and a slow re-widening of exactly what migration 20 narrowed.

- **`p_half_double: false`.** A 64 BPM track *is* harmonically and rhythmically
  compatible with a 128 BPM one, and playing it is a deliberate DJ move — not
  something autoplay should do to you while you are doing something else.
  *(Owner-defaulted 2026-08-05.)*
- `p_sort: 'added_desc'` because the strategy re-ranks everything anyway; the sort
  only decides which 200 rows we see when the window holds more than 200. It must
  **not** be `plays_desc` — see §2.2.
- One fetch per regeneration, hard rule. The fetched window is therefore the bound on
  how far a 24-long harmonic chain can drift, and that is a feature: a set should not
  wander from 128 to 96 BPM without being asked.

### 2.2 A play is a play — no migration

**Decision, owner, 2026-08-05: `bump_play` is untouched and no column is added.**

An earlier draft proposed migration 31 (`play_events.source ∈ {manual, queue,
resume}`) on the argument that M6c ranks "hot this week" by plays, so counting
autoplay's own picks identically closes a feedback loop into a discovery ranking.
The owner's answer is that a play is a play: someone heard the track through, and
that is what the number means. Recorded here so the argument is not rediscovered and
re-litigated in M6c — if the loop ever shows up in real data, the column is a
one-migration fix and this paragraph is the reason to reach for it.

**Two things follow.** `POST /api/track/[id]/play` keeps its exact M6a shape (no
body, 204), and it must now fire on autoplayed tracks too — Task 6 moves
`playMeter.reset()` into the advance path so a queued track counts the same as a
clicked one, which is the direct consequence of "a play is a play".

One place the loop argument still holds and is kept: **`play_count` is not a
tie-break in the harmonic strategy** (§3.5). That is internal ranking, not a
user-visible count, and letting popularity break harmonic ties would make the auto
tail drift toward the same tracks every session for no musical reason.

## 3. The engine / strategy boundary

This is the durable contract. Genre-based and artist-map strategies are explicitly
future work, and the reason they will be *additive files* rather than a refactor is
that the split below gives strategies exactly one job.

### 3.1 The interface

```ts
/** Everything a strategy is allowed to know. Additive by design: a genre
 *  strategy adds `genre` to TrackFeatures and reads it; nothing else moves. */
export interface TrackFeatures {
  file_id: string
  display_artist: string | null
  display_title: string
  duration_ms: number | null
  bpm: number | null
  key_camelot: string | null
  like_count: number
  play_count: number
  created_at: string
}

export interface StrategyContext {
  /** The track the tail continues FROM — the last known-forward entry, NOT
   *  necessarily `current`. See §3.3. */
  seed: TrackFeatures | null
  /** Server-narrowed, pool-visible, already exclusion-filtered by the engine. */
  candidates: readonly TrackFeatures[]
  /** Most-recent-first. For recency-aware ranking, not for exclusion — the
   *  engine has already removed everything in it. */
  history: readonly string[]
  /** How many slots the engine wants. Never negative. */
  need: number
}

export interface Strategy {
  readonly id: AutoMethod
  readonly label: string
  /** Rank and select, in play order. MUST NOT: exceed `need`, re-filter
   *  exclusions (already applied), mutate its inputs, read the DOM, or touch
   *  the network. MUST be deterministic for a given context. */
  select(ctx: StrategyContext): readonly string[]
}
```

### 3.2 Who owns what

| The **engine** owns | A **strategy** owns |
|---|---|
| The 25 cap and the slot arithmetic | Ranking and selection, within `need` |
| Layer 1 — never exposed to strategies at all | — |
| Exclusions (`current`, `intent`, `history`, `failed`, `suppressed`) | — |
| The confirm predicate (§1.5) | — |
| Regeneration on every event | — |
| Fetching candidates (one call, injected as a port) | — |
| Fallback when a strategy returns short | — |
| Persistence | — |

A strategy that returns 400 ids, or an id that is in `history`, is a **bug in the
strategy that the engine silently corrects** — `assembleQueue` truncates to `need`
and re-filters. The correction is asserted in Task 1's tests, so a future strategy
cannot break the cap even if it tries.

### 3.3 The seed is the *last* forward entry, not `current`

Non-obvious and easy to get wrong. If the user has pinned three tracks, the auto tail
must be harmonically compatible with the **third pin**, because that is what will
actually be playing when the tail starts. Seeding from `current` produces a tail that
mixes beautifully out of a track three positions in the past and clashes with the one
immediately before it.

```
seed = last(intent) ?? current
```

Within the chain itself, each pick re-seeds the next — the greedy walk of spec §8.

### 3.4 The four v1 methods

BPM and key only. Genre and artist are out of scope by owner direction, and no
schema for them appears in this milestone.

| id | Label | What it does |
|---|---|---|
| `off` | `OFF` | **Default.** Returns nothing. Short-circuited in the engine — no strategy call, **no fetch**. §1.6. |
| `harmonic` | `MIX` | The greedy Camelot + BPM chain. §3.5. |
| `bpm` | `TEMPO` | BPM proximity only, key ignored. Doubles as the automatic fallback when `harmonic` returns short (§1.3 case 3) — which is the whole reason it exists as a named method rather than an inline branch: the fallback path gets its own tests and its own name in the UI. |
| `shuffle` | `SHUFFLE` | Uniform random over the candidate set, seeded from `current.file_id` so it is deterministic and therefore testable. Not intelligence — the deliberate absence of it. |

**Shuffle is a method, not a modifier.** Spec §8 framed it as a toggle on top of
autoplay. As a peer method it costs one registry entry and no combinatorial state
(`method × shuffle` would be eight configurations to reason about and persist, for
one that anybody wants). *(Owner-defaulted 2026-08-05.)*

### 3.5 Harmonic scoring, spelled out

Spec §8 says the scoring is "salvaged from `useSimilarityFilter.ts`". **That file is
not in this repo or in `~/Projects/cue-parser`** — it lives in butternutcrack, which
we do not have. The plan therefore specifies the scoring outright rather than
pretending to port it. Every constant below is a named export in one place so the
owner can tune them without reading the algorithm.

```
KEY_FREE_HOURS      = 1      // ±1 hour, same letter, is the perfect-fifth /
                             // subdominant move: free, per spec §8.
MODE_SWAP_PENALTY   = 1.5    // A→B or B→A at any distance except 0 hours
RELATIVE_PENALTY    = 0.5    // same hour, other letter: the relative major/minor
UNKNOWN_KEY_PENALTY = 3.0    // no key_camelot — pickable, never preferred
UNKNOWN_BPM_PENALTY = 2.0
BPM_WINDOW          = 0.06   // ±6 %, the server-side gate AND the drift bound
BPM_PCT_DIVISOR     = 3      // 6 % of drift costs 2.0, same order as a mode swap
```

**±1 Camelot hour is free in both directions** — the perfect fifth (+1) and the
subdominant (−1) are both standard mix moves, and the wheel exists precisely so that
either is safe. There is no separate ±1-semitone tolerance: key clash is measured on
the wheel, which is what the Camelot notation is *for*. *(Owner-defaulted 2026-08-05.)*
**The ±6 % BPM window** is a DJ's comfortable pitch range and doubles as the drift
bound of §2. *(Owner-defaulted 2026-08-05.)*

```
keyPenalty(a, b):
  if either key is null            -> UNKNOWN_KEY_PENALTY
  hours = min(|a.n - b.n|, 12 - |a.n - b.n|)          // 0..6
  if hours == 0 and a.L != b.L     -> RELATIVE_PENALTY
  hourCost = max(0, hours - KEY_FREE_HOURS)
  modeCost = (a.L == b.L) ? 0 : MODE_SWAP_PENALTY
  -> hourCost + modeCost

bpmPenalty(a, b):
  if either bpm is null or <= 0    -> UNKNOWN_BPM_PENALTY
  -> (|a.bpm - b.bpm| / a.bpm * 100) / BPM_PCT_DIVISOR

score(seed, cand) = keyPenalty + bpmPenalty      // lower is better
```

Worked values, which are also the table-driven test fixtures:

| seed → cand | penalty | why |
|---|---|---|
| 8A → 8A | 0 | same key |
| 8A → 9A | 0 | perfect fifth — free |
| 8A → 7A | 0 | subdominant — free |
| 8A → 8B | 0.5 | relative major |
| 8A → 9B | 1.5 | mode swap at distance |
| 8A → 10A | 1.0 | two hours |
| 8A → 2A | 5.0 | across the wheel |
| 8A → null | 3.0 | unanalysed |

**Determinism** is a hard requirement (spec §8: "What you see is exactly what
plays"). Ties break in a total order: lower penalty → higher `like_count` → newer
`created_at` → `file_id` ascending. `play_count` is deliberately **not** a tiebreak —
§2.2's last paragraph.

### 3.6 Future strategies (sketch only — no tasks, no schema)

- **Genre.** Once M8 lands a normalised genre facet, a `genre` strategy adds
  `genre: string[]` to `TrackFeatures`, scores Jaccard overlap against the seed's set,
  and blends it with the existing key/BPM penalty. New file, one registry line. The
  engine does not change, because the candidate fetch already goes through a port and
  the cap/exclusion/layer logic never mentions a feature name.
- **Artist maps.** An artist-similarity strategy needs a server-side neighbour lookup,
  which is a new RPC and a new table — both out of scope here. Its *strategy* half is
  still just `select(ctx)`: the map would arrive as an extra field on the context, and
  the engine's contract is unchanged.

The extensibility lives in the interface shape alone. **No genre column, no artist
entity, no similarity table is created by this milestone.**

## 4. UI — the visible queue

- **Where.** A drawer that opens *above* the fixed `.playerbar`, **full width at every
  breakpoint**. Not a side panel on desktop: the player bar is already a full-width
  fixed element at `bottom: 0`, and anchoring the drawer to it keeps one layout to
  reason about, one set of offsets, and one mobile reflow instead of two.
  *(Owner-defaulted 2026-08-05.)*
- **The mobile trap, already documented in the repo.** `.playerbar` reflows to **two
  rows** below 640 px (the seek slider takes its own line), and `.uploadchip-slot`'s
  `bottom` offsets — `3.5rem` desktop, `6.75rem` mobile — are **eyeballed against it
  and cannot be measured from CSS**. That is a live carry in `progress.md`. The drawer
  therefore reuses those exact two numbers as its own `bottom`, in the same CSS block,
  with a comment binding all three together. Opening the drawer adds `body.queueopen`,
  which pushes `.uploadchip-slot` up by the drawer's own max height — one class, one
  rule, naming the coupling instead of hiding it.
- `max-height: 60vh; overflow-y: auto` so a 25-row queue never eats a phone screen.
- **Brutalist idiom, 3-tier buttons.** `--bg` fill, one 1 px `--line` edge, no radius,
  no shadow — the same grammar as `.playerbar` and `.uploadchip`. `☰ QUEUE` toggle and
  per-row `✕` / `↑` / `↓` are `.btn-secondary`; `CLEAR` is `.btn-danger` (it destroys
  the layer-1 list); the method selector is a segmented set of `aria-pressed` buttons
  in the `.likebtn` idiom — a toggle, not an action button, so it takes no `.btn` class
  and no colour token, exactly as `global.css`'s like-toggle block already argues.
  `OFF` is pressed on first load.
- **The seam is visible.** Three labelled sections: `NOW PLAYING`, `YOUR QUEUE` (each
  entry showing its `source_label`, and a `warehouse · 24 of 60` line when a play or
  append was truncated by the cap), `UP NEXT · AUTO — <method label>`. With the
  default method the third section renders one line — *"Autoplay is off. Playback
  stops when the queue runs out."* — and the method buttons beside it. A user must be
  able to see at a glance which part survives a strategy switch.
- **`+ queue` is a companion to play, everywhere play appears.** On track rows

  (the track page). Without JS there is no audio element in use and therefore no
  queue; the drawer never appears. No island: the drawer is vanilla DOM in `site.ts`,
  for the same bundle reason UX.12's store/engine split documents — `Shell.astro`
  mounts on every page, and a queue island would ship the engine, the strategies and
  the candidate client to `/login`.

## 5. Playback mechanics

- **Signed URLs are never prefetched in bulk.** Presigned GETs live one hour
  (`GET_TTL_SECONDS`); a 25-entry queue fetched up front would hold twenty-five URLs
  that expire mid-set. The queue stores **ids and display metadata only, never a
  URL** — the same rule `player-memory.ts` already documents for the resume entry, for
  the same reason. One `/api/track/:id/source` fetch per advance.
- **One lookahead, deliberately small.** At `duration - 20 s` the engine fetches the
  *next* entry's URL into a module variable, so the advance is instant instead of
  round-tripping between tracks. A URL held for 20 s cannot meaningfully expire. A
  second `<audio>` element for true gapless playback is **out of scope**.
- **A dead URL mid-play is already handled and must stay handled.** `refreshSource()`
  (commit `08882d0`) re-signs in place and seeks back. The queue must not race it: a
  failed *refresh* is what fires `TRACK_FAILED`, never a first `error` event. The
  `refreshing` guard already prevents the loop; the engine wiring must not add a
  second path around it.
- **Advance on `ended`.** `TRACK_ENDED` → engine → `queue[1]` becomes current → fetch
  source → play. With `method: 'off'` and an empty layer 1, there is no `queue[1]` and
  playback stops. `clearPlayerMemory()` currently fires on `ended`; with a queue it
  must instead *update* memory to the new current track, and only clear when the queue
  is genuinely exhausted. That is a behavioural change to existing code and Task 6
  owns it explicitly.
- **Play counting.** The M6a meter (`play-meter.ts`, 30 s cumulative, scrub deltas > 5 s
  discarded) and `bump_play` are unchanged — a play is a play (§2.2).
  `playMeter.reset()` must fire on every advance, not only on a click; it currently
  fires in the play-link handler alone, so an autoplayed track would never count.
- **Media Session / lock screen.** `navigator.mediaSession.metadata` from the current
  entry (title, artist, artwork via `artThumbUrl` off the public art bucket — no
  signing, already cacheable). Handlers: `play`, `pause`, `nexttrack` → `SKIP`,
  `previoustrack` → *disabled in v1* (there is no `PREV` event; `history` makes one
  possible later and the field is there for it). Feature-detected: `navigator.mediaSession`
  is absent in some older WebKit contexts and must never throw.
- **Persistence is per-browser, in localStorage.** No server-side queue, no
  cross-device handoff — that would be a new table, a new RPC and a sync story, for a
  ten-member tool where a queue is a thirty-minute artefact. *(Owner-defaulted
  2026-08-05.)*
- **UX.9 resume restores layer 1 only** — `current`, `intent`, `method`, `history`.
  The auto tail is *not* persisted and *not* recomputed at page load: a 14-day-old
  harmonic tail is stale (the pool grew), and recomputing it on load would put a
  `pool_list` call on every returning member's first paint for a drawer they may never
  open. It hydrates lazily on the first of *(drawer opened | playback started)* — and
  with the default `off`, never. Same 14-day TTL, same key convention:
  `localchune:queue:v1` beside `localchune:player:v1`. *(Owner-defaulted 2026-08-05.)*
